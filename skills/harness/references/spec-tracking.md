# 스펙 추적 — 하네스 실행 이력 관리 규격 (신규 하네스 내장 템플릿)

하네스는 한 프로젝트에서 여러 번 실행된다 — 초기 생성, 부분 수정, 파생물 생성, 재검증. 스펙 추적은 각 실행을 **스펙 문서 1건**에 귀속시켜, 무엇을·왜·어떤 입력으로·어디까지 했는지를 프로젝트 폴더 안에 남긴다. 스펙이 없으면 실행 이력은 대화 로그에서만 복원 가능한데, 대화 로그는 프로젝트 밖에 있고 세션이 끝나면 접근성이 급락한다.

**설계 결정 — GitHub Spec Kit의 문서 모델만 차용하고 툴체인은 도입하지 않는다.**

- 차용: 번호 스펙 디렉토리(`NNN-slug/`), 스펙 문서의 수명주기(작성 → 실행 → 완료 기록), 대장(index) 관리
- 미도입 사유: ① 산출물 폴더가 git 저장소가 아닌 경우가 많다 — Spec Kit은 브랜치-퍼-피처를 전제한다. ② Spec Kit의 implement 단계는 하네스의 Phase 파이프라인과 오케스트레이션이 이중화된다. ③ 템플릿이 소프트웨어 기능 명세(유저 스토리·기능 요구) 중심이라 콘텐츠·문서 산출 작업에 맞지 않는다

## Spec Kit 단계 대응 — flow는 하네스가, 게이트는 스펙이

Spec Kit의 clarify→specify→plan→tasks→analyze→implement 흐름은 **절차를 모르는 범용 에이전트에게 절차를 주입하는 장치**다. 하네스는 절차가 Phase 파이프라인(스킬·에이전트)으로 이미 내장되어 있으므로, 스펙은 절차를 재정의하지 않고 **계약(요구·범위·수용 기준)과 게이트(상태 전환)**만 맡는다. 그 flow는 사라진 것이 아니라 아래처럼 분담된다:

| Spec Kit | 하네스에서의 실체 | 담당 |
|----------|------------------|------|
| constitution | 하네스 CLAUDE.md + 공통 작성 규칙 — 프로젝트 불변 | 하네스 자체 |
| specify | 스펙 개설 — 요구(발주 요지)·범위/비범위·입력 스냅샷 | 시작 Phase 훅 |
| clarify | Draft 상태 — 범위 해석이 갈리면 멈추고 확인 후 In Progress 전환 | 시작 Phase 훅 |
| plan | 스펙의 "계획(Phase 매핑)"은 골격만. 상세 설계는 하네스 계획 Phase의 작업 명세 산출물 | 계획 Phase |
| tasks | 태스크 분해가 파이프라인에 고정. 세부 작업 단위는 계획 Phase 산출물이 정의 | 파이프라인 |
| checklist | 스펙의 수용 기준 — 검증 가능한 완료 조건 | 스펙 |
| analyze | 하네스 검증 Phase (리뷰 에이전트·기계 린트) — 수용 기준과 대조 | 검증 Phase |
| implement | 하네스 생성 Phase + 수정 루프 | 생성 Phase |
| converge | 수용 기준 판정 → 완료 기록 → Done → index 갱신 | 최종 보고 Phase 훅 |

### 게이트 규칙 — 언제 멈추나

| 상황 | 게이트 |
|------|--------|
| 발주가 명확한 작업 (부분 수정 등) | 게이트 없음 — In Progress로 개설, 파이프라인 직행. 범위 해석은 결정 기록에 남긴다 |
| 범위가 모호하거나 큰 작업 | **Draft로 개설** → 범위·수용 기준을 사용자와 합의 후 In Progress 전환 |
| 기존 산출물을 대체하는 재실행 | 새 스펙 + 구 스펙 Superseded 전환을 **실행 전에** 확인받는다 |

## 신규 하네스 내장 지침 (Phase 5에서 수행)

하네스를 생성할 때 다음 세 가지를 내장한다:

1. 스펙 디렉토리 규격 채택 — **프로젝트 폴더 최상위 `specs/`** (index.md + `NNN-slug/spec.md`). 하네스 하위에 두지 않는다. 이 파일을 새 하네스 스킬의 `references/spec-tracking.md`로 복사한다 (이 절 "신규 하네스 내장 지침"은 복사본에서 제거)
2. 오케스트레이터의 **시작 Phase**에 "스펙 개설/귀속" 훅, **최종 보고 Phase**에 "완료 기록 → Done → index 갱신" 훅을 넣는다
3. "스펙은 내부 산출물 — 최종 산출물(사용자에게 배포되는 문서·코드·자료)에 스펙 번호를 노출하지 않는다" 규칙을 스킬 공통 규칙에 넣는다

기존 하네스는 일괄 소급하지 않는다 — **다음에 실제로 사용하는 시점에** 그 작업을 스펙 001로 열면서 위 세 가지를 심는다. 과거 실행 이력의 소급 복원은 불가능하므로 "첫 스펙부터 시작"이 정직한 규정이다.

하네스 사본에서 규격을 개선했고 그것이 특정 하네스에 종속되지 않는 일반 개선이면, 이 템플릿에도 반영한다 — 엔진과 설정을 분리하는 원리와 같다.

## 디렉토리·번호 규칙

스펙은 **프로젝트 폴더 최상위 `specs/`**에 둔다. 하네스 하위(`.{하네스명}/specs/`)가 아니다.

```
{프로젝트 폴더}/specs/
├── index.md                 # 스펙 대장 — 전 하네스 공용, 전 스펙의 상태 한눈에
└── NNN-slug/
    └── spec.md              # 스펙 본문
```

- `NNN`: 001부터 **프로젝트 단위**로 증가하는 3자리 번호. 하네스가 여럿이어도 **수열은 하나다**
- `slug`: kebab-case 짧은 영문 (예: `001-day1-lesson-guide`)

**왜 하네스 하위가 아닌가.** 성숙한 프로젝트 폴더는 하네스를 여럿 쓴다(설계 → 산출 → 자동화). 하네스마다 대장을 두면 두 가지가 깨진다.

1. **번호가 충돌한다.** 각 하네스가 001부터 세면 한 폴더에 001이 여럿 생기고, "스펙 21"이 어느 하네스인지 말하지 않으면 지시가 성립하지 않는다
2. **하네스 경계를 넘는 작업에 집이 없다.** 상류를 A 하네스로 고치고 하류를 B 하네스에 남기는 작업은 흔하다. 어느 대장에 넣어도 반쯤 틀린다

대장 표의 **「하네스」 컬럼**으로 구분한다 — 디렉토리가 아니라 컬럼이 그 일을 맡는다.

**이미 `specs/`가 있으면 다음 번호를 이어 쓴다.** 두 번째 하네스가 001부터 다시 세는 것이 충돌의 원인이다. 대장을 새로 만들지 않는다.

## 스펙 귀속 규칙 — 무엇이 새 스펙인가

| 상황 | 처리 |
|------|------|
| 새 작업 요청 (실행 모드 불문) | 새 스펙 개설 |
| 진행 중(In Progress) 스펙의 범위 안 피드백·수정 | 그 스펙의 실행 로그에 기록 |
| Done 스펙 산출물에 대한 추가 수정 요청 | 새 스펙 개설 + 관련 스펙 상호 링크 |
| 오탈자 1~2건 수준의 경미 수정 | 가장 관련 있는 스펙의 실행 로그에 한 줄 추가 (상태 변경 없음) |
| 기존 산출물을 통째로 대체하는 재실행 | 새 스펙 개설, 대체된 스펙은 Superseded로 전환 + 링크 |

## 상태 수명주기

`Draft → In Progress → Done` (+ `Superseded`)

| 상태 | 의미 |
|------|------|
| Draft | 요구·범위 작성 중, 또는 범위 해석에 사용자 확인이 필요해 대기 |
| In Progress | 실행 중 (Phase 진행·수정 루프 포함) |
| Done | 완료 기록까지 작성 완료 |
| Superseded | 후속 스펙이 산출물을 대체 — 후속 스펙 링크 필수 |

사용자가 명시적으로 발주한 작업은 Draft를 거치지 않고 In Progress로 개설할 수 있다 — 발주 요지를 스펙에 남긴다. 범위 해석이 갈릴 수 있는 요청이면 Draft로 두고 확인을 받는다.

## spec.md 템플릿

```markdown
# 스펙 NNN — <제목>

- **상태**: Draft | In Progress | Done | Superseded
- **모드**: <하네스의 실행 모드명>
- **개설**: YYYY-MM-DD · **완료**: YYYY-MM-DD 또는 -
- **관련 스펙**: [NNN](../NNN-slug/spec.md) · 없으면 "없음"

## 요구 (발주 요지)

사용자 요청의 요지를 작업 언어로. 원문 복사가 아니라 "무엇을 왜"로 압축한다.

## 범위 / 비범위

- **범위**: 이번 실행이 만들거나 고치는 산출물
- **비범위**: 이번에 하지 않는 것 — 후속 스펙 후보로 명시

## 입력 스냅샷

| 입력 | 경로 | 기준 시점 |
|------|------|----------|

핵심 입력 파일의 수정 시각·반입 참고자료·선행 산출물을 기록한다.
재실행 시 "그때 입력이 무엇이었나"를 이 표가 답한다.

## 계획 (Phase 매핑)

| Phase | 담당 | 산출물 |
|-------|------|--------|

## 수용 기준

검증 가능한 완료 조건 목록.

## 결정 기록

| 날짜 | 결정 | 사유 |
|------|------|------|

## 실행 로그

| 날짜 | 이벤트 | 결과 |
|------|--------|------|

Phase 완료·수정 루프·중간 피드백을 시간순으로.

## 완료 기록 (Done 전환 시)

- 산출물 목록 (경로)
- 검증 결과 요약
- 남긴 것 — 미해결 이슈·후속 스펙 제안
```

## index.md 템플릿

```markdown
# 스펙 대장 — <프로젝트명>

| 하네스 | 표기 | 산출물 |
|--------|------|--------|
| <하네스명> | `<약칭>` | <산출물 경로> |

| 번호 | 제목 | 하네스 | 모드 | 상태 | 개설 | 완료 |
|------|------|--------|------|------|------|------|
| [001](001-slug/spec.md) | … | `<약칭>` | … | In Progress | YYYY-MM-DD | - |
```

하네스 범례 표는 **그 폴더에서 실제로 쓰는 하네스만** 적는다. 하나뿐이면 표를 생략하고 컬럼만 둬도 된다 — 두 번째 하네스가 들어올 때 표를 세운다.

## 오케스트레이터 훅 — 모든 실행 모드 공통

1. **실행 시작 시** (시작 Phase): `specs/index.md`를 읽고, 이번 요청을 귀속 규칙에 따라 기존 스펙 또는 새 스펙으로 결정한다. 새 스펙이면 spec.md를 작성하고 index에 등재한다. `specs/`가 없으면 이때 만든다 (소급 없음 — 첫 스펙부터 시작).
2. **Phase 경계마다**: 실행 로그에 한 줄 기록 (산출물 경로·결과 요약).
3. **최종 보고 시**: 완료 기록 작성 → 상태 Done → index 갱신. 사용자 보고에 스펙 번호를 밝힌다.
4. **수정 루프**의 라운드별 결과도 실행 로그에 남긴다 — "몇 라운드에 무엇이 닫혔나"가 다음 실행의 참고가 된다.
